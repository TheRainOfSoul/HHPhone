# HHPhone — одноразовые токены вместо пароля в QR (дизайн)

Дата: 2026-10-12. Статус: утверждён в обсуждении, ждёт ревью спеки.
Связано: `2026-10-08-hhphone-design.md` (разделы 4–5 — QR с паролем и блокировка, выпущено в v0.2.0).

## Цель

Распечатанный или пересланный QR для сотрудника не должен раскрывать ни SIP-пароль, ни PIN администратора.
В QR — одноразовый токен; HHPhone по нему один раз забирает учётку у HHPBX по HTTPS, токен сгорает.

## Решения пользователя

| Вопрос | Решение |
|---|---|
| Для каких АТС | Токены — только HHPBX (QR выдаёт панель HHPBX). Для чужих АТС остаётся QR с паролем («Показать QR» на телефоне админа, v0.2.0) |
| Срок жизни токена | Без срока. Одноразовый: сгорает после первого успешного обмена. Отзыв — вручную в панели |
| PIN блокировки | Один на клиента (домен HHPBX): «PIN администратора телефонов» задаётся в панели; при создании QR — галочка «Блокировать» |

## 1. Формат QR и обмен токена

QR: `hhphone://claim?c=<base64url(JSON без паддинга)>`:

```json
{ "v": 1, "server": "https://pbx.orbeli.am", "token": "<base64url 32 байт>", "spki": "<base64 SHA-256 SubjectPublicKeyInfo сертификата>" }
```

- Ни пароля, ни PIN, ни номера.
- `server`: только `https://хост[:порт]`, без пути. `token`: 43 символа base64url. `spki`: 44 символа base64.
- `v ≠ 1` → «обновите HHPhone».

Обмен: HHPhone делает `POST <server>/app/hhphone/claim.php`, тело `token=<token>` (form-urlencoded), таймаут 10 с.

Ответ 200 (`application/json`):
```json
{ "v": 1, "name": "Иван", "user": "201", "pass": "…", "domain": "pbx.orbeli.am",
  "authUser": "", "proxy": "", "transport": "udp", "mediaEnc": "",
  "lock": true, "pinHash": "<base64>", "pinSalt": "<base64>" }
```
- Поля учётки — как в QR v0.2.0 (`HHAccountQr` без `pin`). Валидация на телефоне — та же (`HHQr`): опасные символы → ошибка.
- `pinHash`/`pinSalt` — только при `lock: true`.
- Любая неудача (нет токена, использован, отозван, неверный формат) → 410 и `{"error":"invalid"}`, без подсказок.

### Доверие к серверу

Сертификат принимается, если (а) его признаёт системное хранилище Android, или (б) SHA-256 его SubjectPublicKeyInfo равен `spki` из QR. Проверка имени хоста — только в случае (а); в случае (б) ключ уже закреплён QR. Так самоподписанный HHPBX в локальной сети работает, подмена сервера в сети невозможна, а плановое продление Let's Encrypt не ломает старые QR.

### Блокировка на телефоне

- Телефон заблокирован и нет сессии админа → **сначала** спросить PIN (текущий PIN телефона), **потом** обмен. Иначе отмена ввода PIN сожгла бы токен. Проверку «совпадает ли текущий PIN с доменным» без сжигания токена не делаем: это был бы оракул для подбора PIN.
- После обмена: `lock: true` → телефон сохраняет `pinHash`/`pinSalt` из ответа как свои (PIN становится доменным); `lock: false` → блокировка снимается (как и в v0.2.0: «блокировка берётся из нового QR»).
- PBKDF2 одинаков в HHPhone и HHPBX: HMAC-SHA256, 100 000 итераций, 32 байта, соль — 16 случайных байт в base64, **в функцию передаются байты строки base64-соли (UTF-8)**, результат — base64. Контрольный пример (PIN `4821`, соль `AAAAAAAAAAAAAAAAAAAAAA==`) закрепляется тестами с обеих сторон.

### Ошибки на телефоне

| Ситуация | Сообщение | Токен |
|---|---|---|
| Нет сети / таймаут / сервер не ответил | «Нет связи с АТС. QR не потрачен — попробуйте снова.» | цел |
| Сертификат не прошёл проверку | «Сервер АТС не прошёл проверку безопасности.» | цел |
| 410 | «Этот QR уже использован или отозван.» | — |
| Ответ с неверными данными | «АТС вернула неверные данные учётной записи.» | потрачен |
| Учётка с этим номером уже есть → «Заменить?» → «Нет» | старая учётка остаётся; «QR потрачен» в тексте вопроса | потрачен |

## 2. HHPBX: приложение «HHPhone»

Новое приложение FusionPBX `app/hhphone/` (общий код для Windows и Linux).

### Таблица `v_hhphone_tokens` (описывается в `app_config.php`)

| Поле | Тип | Смысл |
|---|---|---|
| `hhphone_token_uuid` | uuid, PK | |
| `domain_uuid` | uuid | |
| `extension_uuid` | uuid | номер, для которого QR |
| `token_hash` | text, уникальный | SHA-256 (hex) токена; сам токен не хранится |
| `lock` | boolean | блокировать телефон сотрудника |
| `insert_date`, `insert_user` | | кто и когда создал |
| `used_date`, `used_ip` | | когда и откуда обменян (null — не использован) |
| `revoked` | boolean | отозван вручную |

### Страница «HHPhone» (меню; права `hhphone_qr` — superadmin, admin)

- **PIN администратора телефонов** домена (4–8 цифр): хранится в настройках домена (`v_domain_settings`, категория `hhphone`, подкатегории `pin_hash`, `pin_salt`), только PBKDF2 (раздел 1). Смена действует на новые QR; заблокированные телефоны хранят прежний хэш.
- **Номера домена** — у каждого «QR для HHPhone»: галочка «Блокировать» (неактивна, пока PIN не задан) → «Создать» → QR (генератор `resources/qr_code`), «Печать», подпись «Одноразовый: сгорит после сканирования». Новый QR на тот же номер старые не отзывает (два телефона на один номер допустимы).
- **Неиспользованные QR** (номер, когда создан, кем) — «Отозвать». **Журнал** использованных (номер, когда, IP).
- Тексты страницы — ru/hy/en (языковые файлы FusionPBX `app_languages.php`).

### `server` и `spki` в QR

- `server` = `https://<имя домена АТС>` (домен FusionPBX). Показывается над QR.
- `spki` снимается PHP с собственного HTTPS: TLS-подключение к `127.0.0.1:443` с SNI = имя домена, `capture_peer_cert`, SHA-256 от DER SubjectPublicKeyInfo. Не зависит от путей к сертификату на Windows/Linux.

### `claim.php`

- Без сессии панели; только POST; ответ `Cache-Control: no-store`.
- Одна транзакция: `UPDATE v_hhphone_tokens SET used_date = now(), used_ip = :ip WHERE token_hash = :h AND used_date IS NULL AND NOT revoked RETURNING …` — гонка двух одновременных обменов невозможна.
- Учётка: номер, пароль, `effective_caller_id_name` → `name`, домен → `domain`, `transport` `udp`, без прокси и шифрования (как HHPBX по умолчанию). Пароль — текущий на момент обмена.
- `lock` из токена; при `lock: true` и незаданном PIN домена → 410 (QR с блокировкой без PIN не создаётся в панели, но PIN могли удалить).

## 3. HHPhone

- `HHQr.parse` распознаёт `hhphone://claim?c=…` → `HHQrResult.Claim(server, token, spki)`.
- `HHClaim.kt`: обмен токена (корутина `Dispatchers.IO`, `HttpsURLConnection`, свой `X509TrustManager` + `HostnameVerifier` по правилам раздела 1), разбор ответа → `HHAccountQr` + блокировка.
- Создание учётки, «Заменить?», применение блокировки — общий код плана 2 (`HHHost`); новая чистая функция применения блокировки из ответа сервера.
- Строки ru/hy/en во flavor `hh`.

## 6. Автообновление HHPhone (GitHub Releases)

Как в других программах пользователя (HHBlocker, HHDesk): приложение само находит новую версию, спрашивает, скачивает APK и запускает системную установку.

- **Источник** — ссылки на последний выпуск (не API GitHub: у API лимит 60 запросов/час с IP, а у отеля все телефоны за одним IP):
  - `https://github.com/TheRainOfSoul/HHPhone/releases/latest/download/latest.json` — `{"versionCode": 3, "versionName": "0.3.0", "notes": "…"}`;
  - `https://github.com/TheRainOfSoul/HHPhone/releases/latest/download/HHPhone.apk`.
- В каждом выпуске — файлы с постоянными именами `HHPhone.apk` и `latest.json`; их готовит `scripts/release.ps1` (сборка release, проверка подписи, тег, `gh release create`). Пре-релизы и черновики «последними» не считаются — тестовая версия до телефонов не доходит.
- **Когда**: при запуске и при возвращении в приложение, не чаще раза в 6 часов (время последней проверки — в SharedPreferences); пункт меню «Проверить обновления» (в обоих режимах) — сразу. Нет сети — молча пропускаем (ручная проверка — сообщение «Нет связи»).
- **Как**: диалог «Доступна версия X» с заметками → «Обновить» / «Позже» («Позже» — следующая проверка через 6 часов) → скачивание в `cacheDir` с индикатором → если `canRequestPackageInstalls()` = false — экран настройки «Установка неизвестных приложений» для HHPhone, затем установка → системный установщик (`FileProvider`, `ACTION_VIEW`, разрешение `REQUEST_INSTALL_PACKAGES`). Подтверждение — за пользователем.
- **Безопасность**: отдельная подпись не нужна — Android ставит APK поверх только с тем же ключом подписи (`%USERPROFILE%\.hhphone`).
- **Режим сотрудника**: обновление разрешено (не меняет учётки и настройки).
- **Первая версия с автообновлением (0.3.0) ставится вручную**: 0.2.0 его не умеет.
- **Тесты**: JVM — разбор `latest.json` (полный, пустые поля, мусор), правило «новее» по `versionCode`. Живая: на эмуляторе 0.3.0 → выпуск 0.3.1 пре-релизом — не видит; снять пре-релиз — находит и обновляется.

## 4. Тестирование

- JVM (HHPhone): разбор claim-QR (валидные/битые `server`, `token`, `spki`); разбор ответа сервера (полный, без lock, с опасными символами, мусор); применение блокировки из ответа; проверка SPKI на тестовом сертификате; контрольный пример PBKDF2.
- PHP (HHPBX, `windows/tests/t_hhphone.php` в стиле существующих `t_*.php`): создание токена, обмен один раз, повтор → 410, отозванный → 410, мусор → 410, ответ без `pinHash` при `lock: false`, контрольный пример PBKDF2.
- Живая проверка (ВМ hhpbx-test + эмулятор): QR из панели → deep link → учётка зарегистрирована; повтор → «уже использован»; отзыв → «отозван»; блокировка с доменным PIN → «Администратор» принимает этот PIN; QR на заблокированном телефоне спрашивает PIN до обмена (токен цел при отмене).

## 5. Порядок работ

1. **План 3 — HHPBX**: приложение «HHPhone» (таблица, страница, PIN домена, `claim.php`), тест, выпуск HHPBX (bump `windows/VERSION`, сборки Windows и Linux).
2. **План 4 — HHPhone v0.3.0**: claim-QR, обмен, доверие к серверу, блокировка из ответа, автообновление (раздел 6).

## Вне рамок

- TLS для SIP в HHPBX (в выдаваемой учётке пока UDP).
- Отдельная настройка адреса `server` (если имя домена не резолвится в сети клиента).
- Срок жизни токенов (решено: не нужен).
- Сборка для Google Play — без самообновления (Play его запрещает).
